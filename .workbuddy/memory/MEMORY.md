## 业务背景与痛点（2026-09-04 用户口述，已确认）
- 客户的办公用房是**租赁的外部房屋**，非自有房产
- 现有业务系统创建合同时，**强制关联**【办公用房台账】中已建档成功的办公用房
- 办公用房建档要求大量详细信息（产权信息、建设年代等），外部房产**无从获取** → 录不进去
- 客户期望：按附件3统计表**直接导入**，绕开逐条建档
- **问题本质**：系统把「自有房产档案」与「外部租赁房源」压成同一实体，
  产权证号/建设年代设为必填 → 租赁房源落不了库 → 合同创建被阻塞

## 台账结构与关联约束（2026-09-04 用户口述，已确认）
- 合同**不关联资产**的后果：无法形成办公用房租用台账，无法记录租用楼栋/房间内的办公人数
- 现有系统表单按「**产权为自身**」设计，租赁房产填不进去
- 客户期望：**一步导入**
- 由此构成两难：关联 → 填不进；不关联 → 台账断裂、人均面积核算断供

### 三层问题拆解（分析推导，非用户原话）
1. 表单字段不适配 —— 可改，属技术问题
2. 台账连续性不能断 —— 合同浮在台账外则人均面积算不出，系统失去核心价值
3. **导入粒度先天不足** —— 附件3 只到「地址级」（单位/地址/总面积），
   台账需要「房间级」（楼栋/楼层/房间/使用部门/办公人数），中间断层导入填不出来

### 🎯 需求目标（用户 2026-09-04 最终表述，以此为准）
- **合同创建时兼容「自建楼栋」与「租用楼栋」两种类型** —— 两种都要能建、能选、能关联
- 由此明确：问题不是"合同要不要关联资产"，而是"被关联的两类楼栋如何统一建模"

### 聚焦楼栋后的核心问题
- 阻塞点从「合同关联资产」细化到「**楼栋建档本身**」
- 若楼栋实体同样必填产权证号、建设年代等，租赁楼栋照样落不了库，问题只平移了一层
- 附件3「租赁地址」是自由文本（示例：XX区XX路XX号XX楼XX层XX房间号），
  需判定能否结构化出楼栋，以及整栋租 vs 部分租的表达方式

### 数据模型改造要点（改造对象为楼栋实体，统一实体不拆两个）
- 楼栋实体新增「取得方式」（自建 / 租用，必填）
- 字段分三组：**共有字段**（楼栋名称、地址、建筑面积、层数、用途）两类均必填；
  **自建专属**（产权证号、产权单位、账面价值、用地性质、建成年代、房屋结构）；
  **租用专属**（出租方、租期起止、年租金、租金来源、是否备案）
- 取得方式决定显示与校验：自建不出现租赁字段，租用不出现产权字段，互不阻塞
- 房间层（下游业务）沿用既有结构，挂楼栋之下，不区分自建与租用

### 合同侧改造要点（用户关注的落点）
- 关联楼栋的选择器**只有一套，不按类型分支**，两种楼栋都能选
- 楼栋不存在时提供**内联新建**入口，不跳出台账模块，建完自动回填关联
- 从合同进入新建时用合同已有信息**预填**（出租方、租期、租金、用途），避免重复录入
- 导入附件3 走同一套规则：每行自动建「取得方式=租用」的楼栋 + 合同 + 关联

### ✅ 已拍板（2026-09-07 用户答复）
- **租赁合同的标的必须精确到房间级**（租一层 = 该层的房间集合，租一间 = 单个房间）
- 由此推翻 09-04「合同只到楼栋级 → 一步导入成立」的结论：
  **附件3 一行只有「地址 + 总面积」，无房间明细 → 无法一步导入出房间级标的**
- 连带结论：
  1. 楼栋这一层躲不掉（房间必须挂在 楼栋→楼层 之下），只能让它「变轻」，不能跳过
  2. 必须有**房间批量生成**能力（按层批量建房间；整层/整栋租时的虚拟拆分与后续细化）
  3. 「一步导入」需降级为**两段式**：第一段建楼栋+楼层+合同+租赁总面积并即时生效；
     第二段房间明细后补，用「已分配面积 / 总租赁面积」进度驱动
  4. 「取得方式」不能只挂楼栋级，需支持**楼栋默认 + 房间级可覆盖**（应对部分租部分自有）
- 客户要的「一步导入」本质是**不想逐条建档**，不是要求数据一次性完整 →
  两段式不违背客户诉求，只要不产生重复录入
